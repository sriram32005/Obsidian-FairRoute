# 2. Problem

## Problem Statement

**What precise problem does this paper solve?**

Existing inference serving systems are extremely inefficient at handling the multi-iteration workload required by Transformer-based generative models. Because models like GPT generate text autoregressively—running the model once for every single token generated—individual requests require varying numbers of iterations to complete

Current systems use **inflexible request level scheduling** . This locks the entire batch in the engine until every request in that batch is executed. Basically run the entire model every time for each token in each batch. 

## Why Does This Problem Matter?

- **Early-finished requests:** Requests that require fewer tokens finish early but cannot immediately return to the client; they are held back until the longest request in the batch completes. This heavily inflates latency and forces the engine to perform wasteful extra computation on inactive requests.
    
- **Late-joining requests:** Newly arrived requests cannot dynamically join an active execution batch. They are forced to wait in a queue until the ongoing batch finishes entirely, which severely increases queueing delay and limits overall system throughput.

- **Generative models:** All LLMs and latest ai models are generative and requires language generations, even traditional translation tasks or NLPs require generation. Poor serving approaches lead to massive resource wastage and latency.

- **Strict Production Constraints:** To be viable in real-world applications, an ML inference service must be able to process client requests with both low latency and high throughput, all while keeping operational costs within a reasonable limit. This is crucial to manage real world tasks that come with huge requests. Also, Under existing systems, operators face a severe trade-off: they either have to run small batches to maintain acceptable latency (which ruins throughput and wastes hardware potential) or run large batches to maximize throughput (which drastically inflates latency for early-finishing requests).

# 4. Core Contribution

## Core Insight

> What is the **one central idea** that distinguishes this paper?
	The fundamental mismatch between traditional request-level batching and the autoregressive, token-by-token generation process of Transformer models wastes significant compute and heavily inflates latency. By shifting the scheduling granularity from the entire request to a single iteration (one token generation), a serving system can dynamically modify the active batch at every step, allowing finished requests to return to the client immediately and new requests to join without waiting for the longest ongoing request to complete.
## Main Contributions
- Identifying the severe efficiency and latency bottlenecks caused by early-finished and late-joining requests in existing inference systems like Triton and FasterTransformer.
    
- Proposing iteration-level scheduling to dispatch execution engine workloads at the granularity of a single token generation.
    
- Developing selective batching to enable efficient GPU execution on irregularly shaped batches containing requests at completely different stages of generation.
    
- Designing and implementing ORCA, a distributed serving system capable of scaling to models with hundreds of billions of parameters using intra-layer and inter-layer parallelism.
    
- Demonstrating through evaluation that ORCA achieves up to a 36.9x throughput improvement over state-of-the-art systems at the same median latency.
## What Is Actually Novel?
-  **Iteration-Level Scheduling for Generative Models:** While prior RNN systems explored fine-grained batching, ORCA is the first to apply iteration-by-iteration scheduling specifically to the continuous batching of Transformer models, discarding the static request-level batching paradigm.

- **Selective Batching:** Because requests in different phases have different input shapes, they cannot be batched traditionally. ORCA introduces a technique that flattens inputs to collectively batch non-Attention operations (e.g., Linear, LayerNorm, GeLU) across all heterogeneous requests, while using distinct Split and Merge operations to process the unbatchable Attention computations individually.
    
- **Control and Data Plane Separation:** Existing distributed engines like FasterTransformer sync CPUs and GPUs using NCCL for both control and data, causing overhead at every iteration. ORCA introduces a novel separation for inference by routing CPU control messages via gRPC and reserving NCCL exclusively for GPU-to-GPU intermediate tensor data transfers.
    
- **Microbatch-Free Pipelining:** ORCA completely bypasses the need to split batches into microbatches for inter-layer pipeline parallelism (a requirement in FasterTransformer), preventing pipeline bubbles and maintaining maximum batching efficiency across multiple workers.

# Fundamental Concept - The iteration level scheduling and selective batching

Autoregressive generative models process sequences token-by-token, meaning the computational lifespan of every request varies drastically based on the required output length. Legacy serving systems blindly apply static, request-level batching, which traps short requests in the execution engine until the longest request finishes. This architectural rigidity forces GPUs to perform wasteful computations on inactive requests while forcing newly arrived requests to queue uselessly until the entire batch flushes.

**System Overview** ORCA is a distributed inference serving system explicitly engineered to break the latency-throughput deadlock of Transformer-based generative models. It functions via a tightly integrated scheduler and execution engine that continuously mutates the active batch at the granularity of a single token generation, scaling efficiently across multiple GPUs for models with hundreds of billions of parameters.

# Architectural Breakthroughs

- **Fine-Grained Execution Engine (Iteration-Level Scheduling):** Instead of committing to a locked batch of requests, ORCA’s scheduler drives the engine to execute only a single model iteration at a time. Upon completing an iteration, the engine immediately returns the generated tokens to the scheduler. This loop allows ORCA to instantly return results for early-finished requests to the client and inject late-joining requests into the very next iteration, eliminating structural queueing delays.
    
- **Operation-Aware Tensor Fusion (Selective Batching):** Iteration-level scheduling naturally mixes requests in the "initiation phase" (processing full multi-token prompts) with requests in the "increment phase" (generating single tokens). Because their input dimensions do not match, standard batching fails. ORCA resolves this by flattening the input tensors to collectively batch structure-agnostic operations (Linear, LayerNorm, GeLU). For the Attention operation—which strictly requires request-specific context—ORCA dynamically inserts a Split operation to process each request individually, followed by a Merge operation to re-fuse the batch for the remaining network layers.
    
- **Deadlock-Free State Tracking (Attention K/V Manager):** Because ORCA constantly rotates requests in and out of the active batch, it must carefully manage the historical Attention keys and values required for text generation. To prevent the engine from stalling or running out of memory mid-generation, ORCA evaluates a request's `max_tokens` attribute at arrival. The scheduler statically pre-reserves the exact number of GPU memory slots required for that specific request before admitting it into the execution pool, ensuring safe continuous batching.
    
- **Asynchronous Engine Orchestration & Microbatch-Free Pipelining:** Existing distributed execution engines suffer from heavy CPU-GPU synchronization overhead because they transmit both control instructions and tensor data over the same NCCL channels at every iteration. ORCA splits this architecture: it routes CPU-level control messages via gRPC and restricts NCCL entirely to GPU-to-GPU tensor transfers. This decoupled communication allows ORCA to seamlessly pipeline full batches across inter-layer workers without ever needing to fracture batches into less efficient "microbatches"

## Scheduling Algorithm

![[Pasted image 20260904224350.png]]

**Core Scheduling Principles**

- **Iteration-Level FCFS:** The scheduler maintains an ordered request pool where earlier-arriving requests are guaranteed to have executed the same or more iterations than later-arriving ones. However, shorter late-arriving requests can still finish and return to the client earlier.
    
- **Batch Size Limits:** To balance the tradeoff between throughput gains and latency penalties, the scheduler enforces a configurable `max_bs` (maximum batch size) limit.
    
- **Deadlock Prevention:** Unlike intermediate computation buffers, Attention K/V caches must persist across multiple iterations until a request fully completes. If the engine runs out of K/V slots mid-generation, the system will deadlock. ORCA prevents this by forcing the scheduler to track and pre-allocate memory.
    

**Algorithm 1: Scheduling and Resource Allocation Logic** The scheduling algorithm operates as a continuous loop managing a state machine of requests (`INITIATION`, `RUNNING`, `INCREMENT`) while dynamically allocating fixed memory resources.

- **Request Selection (`Select` function):** The algorithm filters the pool for non-running requests, sorts them by arrival time, and iterates through them to build a batch up to the `max_bs` limit.
    
- **Memory Reservation:** For any request in the `INITIATION` phase (its first iteration), the scheduler checks if adding its required `max_tokens` to the currently reserved slots (`n_rsrv`) exceeds the total hardware capacity (`n_slots`). If the limit is exceeded, the algorithm breaks and stops adding requests to the batch to prevent memory exhaustion. If the capacity allows, the slots are reserved, guaranteeing the request can complete its generation process.
    
- **Asynchronous Dispatch:** The main loop dispatches the selected batch to the execution engine. To maintain high hardware utilization, it keeps a number of batches in flight equal to `n_workers` before waiting for a return.
    
- **State Updates and Reclamation:** When a batch returns from the engine, the scheduler transitions those requests to the `INCREMENT` phase. If a request has finished, its pre-allocated `max_tokens` are subtracted from `n_rsrv`, safely freeing the memory slots for new arrivals.
    

**Pipeline Parallelism: ORCA vs. FasterTransformer** The text highlights how iteration-level scheduling inherently improves pipeline parallelism across multiple workers (inter-layer partitions) compared to existing engines.

- **FasterTransformer (Microbatching):** Bound by request-level scheduling, this system cannot inject a new request (e.g., Request C) until the currently executing batch (A and B) completely finishes. To keep multiple inter-layer partitions busy, it must artificially split the single active batch into smaller "microbatches" (A, then B) to push through the pipeline. This shrinks the effective batch size—degrading batching efficiency—and can introduce idle pipeline "bubbles" if the microbatch size is too large.
    
- **ORCA (Continuous Batch Pipelining):** Because ORCA schedules at the iteration level, it does not need to wait for a request to fully complete. It continuously injects newly formed batches (e.g., batch AB, then batch CD, then batch EF) directly into the pipeline. Worker 1 processes batch AB and immediately moves to CD, while Worker 2 receives AB, maintaining full pipeline saturation. This completely eliminates the need for microbatches, maximizing both batching efficiency and hardware utilization without structural tradeoffs

# Implementation and Evaluation Setup

- ORCA is built in C++ and CUDA, utilizing gRPC for control messages, NCCL for data transfers, and custom fused kernels—including a novel fusion of split Attention operators across varying tensor shapes—to maximize GPU utilization.
    
- The system was evaluated on Azure A100 GPU clusters running distributed GPT models scaled from 13 billion up to 341 billion parameters using fp16 precision.
    
- Performance was benchmarked against FasterTransformer through both static execution engine microbenchmarks and dynamic end-to-end synthetic workloads driven by a Poisson arrival process.

# Experimental Setup and Methodology 

The evaluation benchmarks ORCA on Azure A100 GPU clusters against NVIDIA's FasterTransformer, using distributed GPT models ranging from 13 billion to 341 billion parameters. The authors use two testing scenarios to isolate performance variables: a static engine-only microbenchmark to test raw execution efficiency, and a dynamic end-to-end emulation using a Poisson arrival trace to simulate real-world, highly variable generative workloads.

When evaluating raw engine execution without the scheduler, ORCA performs comparably to FasterTransformer on single-GPU setups but outperforms it by up to 47% on large, multi-GPU models like the 175B GPT. This scaling advantage is driven by ORCA's decoupling of control and data planes, which drastically reduces inter-layer synchronization overhead. Additionally, ORCA avoids the out-of-memory errors that plague FasterTransformer at larger batch sizes by pre-allocating KV cache memory based strictly on a request's specific maximum token limit, rather than defaulting to the model's absolute maximum sequence length of 2048.


Under realistic traffic conditions with variable prompt lengths and generation targets, ORCA demonstrates massive efficiency gains, delivering a 36.9x throughput improvement over FasterTransformer at the same median latency on the 175B model. FasterTransformer struggles heavily with these variable workloads because its strict request-level batching forces the system to pad short requests and traps finished queries behind long-running ones. ORCA's iteration-level scheduling effortlessly absorbs these variances, safely scaling throughput alongside batch size by dynamically rotating finished and new requests in and out of the batch iteration by iteration.

  
Even when the workload is artificially constrained to homogeneous requests—meaning every request has the exact same input and output lengths to eliminate the early-leaving bottlenecks—ORCA continues to outperform FasterTransformer. This exposes a fundamental flaw in FasterTransformer's pipeline parallelism, which requires fracturing batches into smaller, less efficient "microbatches" to keep workers busy. ORCA bypasses microbatching entirely, maintaining full batching efficiency and continuous pipeline execution across all its workers.

# Final Conclusion and summary
ORCA redefines the serving architecture for autoregressive Transformer models by replacing static request-level batching with iteration-level scheduling. By executing models one token generation at a time, it dynamically cycles finished and new requests in and out of the active batch, entirely eliminating structural queueing delays. To support this continuous flow, selective batching flattens structure-agnostic operations while processing unbatchable Attention computations individually, and a dedicated K/V manager pre-allocates memory slots per request to prevent deadlocks. Paired with a decoupled control and data plane that eliminates the need for microbatching, the system maximizes hardware utilization and pipeline efficiency for massively scaled language models.

**Key Performance Metrics & System Specifications**

- **Throughput Gains:** Achieves a 36.9x throughput improvement over FasterTransformer (6.81 req/s compared to 0.185 req/s) at a matched median normalized latency of 190ms on the 175B parameter model.
    
- **Engine Efficiency:** Outperforms FasterTransformer's raw engine execution by up to 47% on multi-GPU setups (175B model) due to the separation of control and data planes.
    
- **Model Scaling:** Evaluated across GPT configurations of 13B, 101B, 175B, and 341B parameters, with all models using a maximum sequence length of 2048.
    
- **Implementation:** Built with 13,000 lines of C++ relying on the CUDA ecosystem, utilizing gRPC for control messages and NCCL for tensor data transfers.
    
- **Hardware Setup:** Tested on up to four Azure ND96asr A100 v4 VMs, utilizing a maximum of 32 NVIDIA 40-GB A100 GPUs connected via NVLink and 1.6Tb/s Mellanox HDR Infiniband

## Main Takeaway
The fundamental takeaway of the ORCA paper is that applying legacy request-level batching to autoregressive Transformer models creates severe computational bottlenecks, as early-finishing requests are trapped and new requests are blocked. To solve this, ORCA shifts execution to **iteration-level scheduling**—processing requests at the granularity of a single token generation—which allows the system to dynamically cycle finished and new requests in and out of the active batch. Because requests at different stages of generation cannot be batched normally, ORCA pairs this with **selective batching**, which flattens shared operations (like Linear and LayerNorm) and processes Attention computations individually. This architecture eliminates wasted GPU cycles and structural queueing delays, yielding up to a 36.9x throughput improvement over state-of-the-art systems like FasterTransformer at the same median latency.
